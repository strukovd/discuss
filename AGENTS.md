# Стиль кода проекта

## Vue-компоненты

- Не использовать `scoped` стили в `.vue` компонентах.
- Не использовать BEM-нейминг для локальной разметки компонентов.
- Держать стили компонента в том же `.vue` файле, если нет явной причины вынести их отдельно.
- Использовать короткие структурные классы, совпадающие с шаблоном компонента.
- Не привязывать стили к смысловым HTML-тегам (`span`, `b`, `p`, `h*` и т.п.), если по стилям нужно понять роль блока. Давать таким элементам осмысленные классы.
- Для простых и часто повторяющихся локальных классов (`title`, `content`, `address`, `footer`, `value`, `status` и т.п.) использовать префикс компонента/страницы. Например для `complaint-details` использовать `cd-title`, `cd-content`, `cd-address`.

## Структура SCSS

- Использовать вложенность SCSS.
- Иерархия стилей должна повторять HTML-иерархию.
- Если шаблон выглядит так:

```html
<div class="wrapper">
	<div class="content">
		<span class="message"></span>
	</div>
</div>
```

то SCSS должен выглядеть так:

```scss
.wrapper {
	.content {
		.message {
		}
	}
}
```

- Не сплющивать вложенную структуру компонента в селекторы вида `.wrapper-content-message`.
- Использовать `&` только для классов состояния и псевдоселекторов, например `&.active`, `&:hover`, `&:focus-visible`.


## Примечания
- Важные примечания\правила\стиль\стандарт из чата выписывать сюда, для построения общих правил проекта.
- Не плодить мелкие helper-функции для одноразовой простой логики. Если inline-код читается понятнее, оставлять inline.
- Держать примерно один уровень абстракции в файле: функции выносить только когда они описывают доменную операцию, используются повторно или заметно упрощают чтение.

- Повторяющиеся вкладки реализовывать через `BaseTabs`, сохраняя общий интерфейс и стиль компонента.
- Операции с данными и будущим backend держать в `app/services`, группируя по доменам. Заглушки использовать через тот же сервисный интерфейс; не размещать хранение данных и API-вызовы в компонентах страниц.
- Перед созданием базовых компонентов учитывать доступные образцы и сохранять полезные возможности (иконки, loading, слоты), адаптируя их к текущему UI.
- Разрабатывать поэтапно: за этап делать одну фичу или страницу, затем останавливаться для просмотра пользователем. Следующий этап начинать после его указания.
- Сначала разрабатываем frontend с заглушками. Backend приложения на NestJS и отдельный ИИ-сервис относятся к следующим этапам.
- Интерфейс светлый, с лёгким векторным стилем и основным синим цветом. Уместные векторные иллюстрации можно использовать, например, для пустых состояний.
- Не добавлять в документацию названия и пути сторонних внутренних проектов, используемых как образцы для разработки.
